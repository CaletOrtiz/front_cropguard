# H-09 Persistencia de sesión Supabase en Android

Fecha: 2026-11-16. **ID propuesto H-09**, categoría **OWASP Mobile M9 Insecure Data Storage**. Severidad propuesta: alta, por la posibilidad de reutilizar tokens si se extrae la sesión del almacenamiento o de un respaldo. Se verificó el DOCX y H-09 no está usado: los IDs encontrados son H-01, H-02, H-03, H-04, H-05 y H-08. No se modifica el informe original.

Estado: deficiencia confirmada, corrección integrada y APK release verificado. Las pruebas físicas de Android quedan pendientes; no se presentan mocks como prueba de cifrado en hardware.

Frontend limpio al inicio, HEAD `4ad5cbe` (H-01). El backend tenía los cambios previos de H-01 en `.gitignore` y la retirada de Repomix; este hallazgo no modifica el backend.

Se verificaron las versiones realmente resueltas en `pubspec.lock` y `.dart_tool/package_config.json`: Flutter **3.47.5**, Dart **3.13.4**, `supabase_flutter` **2.18.0**, `gotrue` **2.27.2**, `shared_preferences` **2.5.6** y su plugin Android **2.4.28**. No se actualiza Supabase ni se adopta una API de una versión diferente.

## Integración aplicada

Se añade `flutter_secure_storage` **11.2.0** y se configura para Android con un namespace propio, **AES-GCM** para los datos y **RSA-OAEP** para proteger la clave mediante **AndroidKeyStore**. No se usa `encryptedSharedPreferences` de Jetpack Security. La versión instalada de Flutter y el plugin tienen mínimo Android API 24, por lo que no fue necesario cambiar el mínimo de la app.

`AndroidAuthStorage` implementa el contrato `LocalStorage` del SDK instalado y proporciona además un `GotrueAsyncStorage` para PKCE. Se conecta mediante `FlutterAuthClientOptions.localStorage` y `pkceAsyncStorage`; Supabase sigue gestionando expiración, renovación, restauración y eventos. No se crea un segundo sistema de autenticación.

La clave lógica de la sesión conserva el nombre utilizado por el SDK. En la primera apertura:

1. Se comprueba si ya existe la copia segura; esta tiene prioridad sobre cualquier copia legada antigua.
2. Si solo existe la sesión anterior, se copia íntegramente al almacenamiento seguro y se vuelve a leer para comprobar la copia.
3. Se elimina la copia anterior de SharedPreferences. El resultado nativo del borrado se comprueba y se recargan las preferencias para verificar la ausencia.
4. También se migra el verificador PKCE de la versión instalada, `supabase.auth.token-code-verifier`.

El almacenamiento legado es de solo lectura/borrado para esta migración: no permite persistir nuevos tokens. Si falla la copia cifrada, la inicialización falla con un mensaje genérico y conserva la única copia anterior para reintentar; no restaura la sesión desde texto claro como fallback. En ese caso la migración aún no está completada y no se acredita la eliminación del dato anterior.

Las escrituras y eliminaciones del adaptador se serializan para evitar que una escritura ya en curso reaparezca después del cierre. `SupabaseAuthService.signOut()` espera además el borrado local, incluso si falla la llamada remota de cierre. Ese adaptador se pasa desde la composición actual en `lib/app.dart`. Los flujos de correo, registro y Google siguen utilizando el mismo cliente Supabase; el intercambio de ID token no cambia.

Se mantiene `resetOnError: false` para no borrar silenciosamente el almacén ante errores de Keystore. Un fallo de acceso seguro interrumpe la inicialización; la recuperación de un Keystore dañado puede requerir borrar los datos locales de la app y autenticarse de nuevo. Los errores nuevos no interpolan tokens, JSON de sesión ni detalles de excepciones nativas.

## Respaldo y compatibilidad

El manifiesto referencia `auth_backup_rules.xml` para Android anteriores a 12 y `auth_data_extraction_rules.xml` para Android 12 o posterior. Se excluye el dominio `sharedpref` completo tanto del respaldo en nube como de la transferencia entre dispositivos. Esto incluye la sesión anterior, el almacén cifrado y el material de claves envuelto que utiliza el plugin.

El efecto también alcanza otras preferencias locales: no se restaurarán por esos canales. No cambia el almacenamiento remoto de fincas, perfiles o diagnósticos en Supabase. No se exige biometría ni un diálogo adicional para reabrir la sesión.

La selección del adaptador se limita a Android nativo. Web y los otros sistemas conservan el almacenamiento que usaban con el SDK; no se afirma protección mediante Keystore en esas plataformas. Flutter generó actualizaciones de registro del plugin para Linux, macOS y Windows, que se conservan junto a la dependencia.

El código Java resuelto del plugin usa `KeyStore.getInstance("AndroidKeyStore")` en `KeyCipherImplementationRSAOAEP.java` y `AES/GCM/NoPadding` en `StorageCipherImplementationGCM.java`. La integración con Keystore no garantiza que todos los dispositivos tengan StrongBox o TEE; el nivel hardware debe medirse en un dispositivo.

## Verificación

Pruebas nuevas con datos exclusivamente sintéticos:

- Comparación del almacenamiento predeterminado del SDK, que conserva JSON legible.
- Migración de sesión y PKCE, borrado del origen y reapertura con otra instancia del adaptador.
- Prioridad del estado seguro sobre una copia legada obsoleta.
- Fallo de migración sin restauración desde texto claro ni pérdida de la única copia.
- Escritura en curso seguida de cierre, sin resurrección de sesión.
- Persistencia de PKCE mediante la API segura y borrado al cerrar.
- Selección del adaptador en Android y conservación de la selección anterior en escritorio.
- SDK Supabase real y `AuthRemoteDataSource`: inicio con correo, consulta de perfil, renovación, destrucción/recreación del cliente, recuperación de usuario, cierre y nueva reapertura sin sesión. Se prueba también el intercambio de ID token usado tras obtener credenciales nativas de Google.

**Las 8 pruebas específicas pasaron.** La persistencia del SDK es asíncrona; las pruebas esperan la escritura mediante el adaptador o una señal de la API simulada, en vez de suponer que una respuesta de autenticación significa que terminó toda escritura en disco. Se completaron los metadatos del cliente HTTP de prueba que requiere PostgREST. Estas correcciones son del fixture de pruebas.

## Comprobaciones físicas pendientes

`adb devices` no detectó dispositivos. Quedan pendientes, usando una cuenta de prueba y sin capturar valores:

1. Actualizar una instalación con sesión legada: abrir, confirmar que continúa autenticada y que el token ya no está en las preferencias legadas.
2. Verificar que el almacén nuevo contiene datos cifrados, que usa Android Keystore y medir `KeyInfo.getSecurityLevel()` si se necesita acreditar TEE/StrongBox.
3. Iniciar sesión por correo y Google, cerrar el proceso desde Android y reabrir; repetir tras una renovación.
4. Cerrar sesión y reabrir: debe seguir desautenticada y sin sesión ni verificador persistidos.
5. Comprobar las exclusiones de respaldo/restauración y transferencia en Android anteriores y posteriores a 12, así como los casos de error de almacenamiento. Una copia antigua creada antes de esta actualización no se elimina del servicio de backup mediante esta corrección.

Este hallazgo protege la persistencia de sesión en Android; no acredita la protección de todos los archivos sensibles de la app, la autorización sobre recursos del backend ni las políticas RLS.
